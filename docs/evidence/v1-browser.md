# V1 controlled browser evidence

Actual local implementation and verification, 2026-11-01. This report covers the controlled Chromium host and synthetic site only. It does not establish compatibility with any of the five agents' native browsers, real websites/accounts, or deployment.

## Delivered files and trusted boundary

- `src/browser.ts`: `createControlledBrowserHost`, narrow dependency interfaces, and `browserVaultCapabilities` mapping to the actual Vault's encrypted material callback, security epoch, durable operation journal and request tickets.
- `src/browser-demo.ts`: actual loopback HTTP login form, same-origin frame form, synthetic session cookie, expiry behavior, counted authenticated submissions, and deliberate disconnect after accepting a submission. Request bodies and passwords are not retained or logged.
- `src/browser-demo-run.ts`: runnable standalone synthetic demonstration using a new temporary encrypted Vault, sandboxed Chromium, separate fill and submit approvals, and session reuse. Its finally block closes the server/browser and removes the temporary Vault.
- `tests/browser.test.ts`: real `/usr/bin/chromium` tests; no mocked DOM/Chromium. Most adversarial host tests inject capabilities and a temporary SQLite journal; the integration test uses the actual Vault, signed request tickets, encrypted SQLite, and durable restart recovery.

Only expose the returned `execution` surface to an authenticated agent. The server must map authentication to `Authority`; tool callers must never supply their own authenticated principal. Keep `control` in the trusted manager, including `approveFill`, `approveSubmit`, host lifecycle, and the test/host-only Page accessor. Approval calls in the synthetic runner are explicit trusted-manager stand-ins, not evidence of a management UI integration. There is no public HTTP browser approval route or browser MCP tool wired in this change.

The host creates fresh, nonpersistent contexts itself. Callers can select only a registered site ID and opaque server-issued session/approval IDs. They cannot register a caller-owned Page, asserted origin/document/frame identity, arbitrary selector, URL or script. Bindings include adapter/host instance, owner, authenticated principal, context, tab, frame/loader IDs, top document, exact origins, security epoch, and rule version. Fixed rules are copied/frozen; production rules require HTTPS, while HTTP is permitted only for an explicitly synthetic 127.0.0.1 rule. The registered standalone synthetic target uses port 43122; isolated unit fixtures use random loopback ports.

Chromium CDP provides frame/loader identities. A separate isolated world retains the original document and documentElement plus top-document identities; final checks and native field setters execute in one synchronous renderer task. Same-origin navigation/reload, fragment navigation, document.open replacement, frame-tree changes, context close, or a new host invalidate handles. Main-world prototype replacement cannot replace the isolated world's native setters/submit primitive. No input/change events, click, Enter or submit occur during fill.

Handles expire after 5 minutes without renewal. Separate 60-second single-use approvals bind record/content version and status version, fixed rule/version and the full session binding. Revocation/pause followed by reactivation cannot revive an approval because the status version changed. TTL/epoch/record/status/policy are checked again before actual secret dispatch. A handle can fill once; concurrent fills consume only one approval. Secret output, input DOM reads, screenshots, HAR, trace, video, console forwarding and generic browser tools are absent from the execution surface. The trusted site can see the password in its DOM, and trusted host memory/Chromium necessarily sees plaintext; this does not claim isolation from same-UID/root or a compromised trusted host/site.

## Submission and unknown outcomes

`login_submit` requires its own approval after fill. It validates a visible fixed form, associated username/password controls, exact same-origin POST action, `_self` target and URL-encoded form encoding. A durable journal writes accepted/dispatching before dispatch; only filtered status and HTTP status enter the result. Redirects are not followed for submit. A reset, timeout, disconnect, non-2xx HTTP status or ambiguous failure returns `outcome_unknown`; replay returns the stored state, and unresolved same-connection/operation/business-target conflicts block new tickets. HTTP error status alone cannot prove no side effect: the site can commit login and then return 500. No generic HTTP error becomes `failed_confirmed`.

An initial real Chromium test found that Chromium can internally retry a reset POST even when the host invokes native submit once and the context allows only one routed Request. The final implementation therefore dispatches the approved fixed navigation POST through Playwright's request route with `maxRetries: 0` and `maxRedirects: 0`, then fulfills/aborts the renderer request. The one-request permit additionally rejects other non-GET/HEAD traffic. The synthetic server sees exactly one authenticated POST when it deliberately disconnects after accepting. This constrains host/browser dispatch; it does not claim external exactly-once execution or eliminate a proxy/upstream's own duplicate behavior. Playwright may transiently buffer the submit response to fulfill the browser; it is not persisted, logged, or returned to the agent.

The real Vault integration creates and approves a synthetic password record, fills Chromium without submitting, approves submit separately, accepts once then disconnects, and restarts both Vault and host. It verifies same signed-ticket replay, different-payload conflict, rejection of a forged ticket, rejection of a new signed ticket while unknown, old handle invalidation after lock/unlock, and absence of the synthetic password bytes from SQLite and returned results. The pure host SQLite fixture also exercises replay after journal reconnection. Core crash recovery for persisted `dispatching` is provided by Vault; this browser suite tests full restart after a persisted unknown result, not a process-kill-at-instruction crash injection.

Success cases prove main-frame and same-origin-frame fill, no automatic submission, distinct submit approval, cookie session reuse, and expired session requiring login.

## Review fixes and lifecycle verification

Independent review correctly found that merely rejecting expired handles left contexts/password DOM/cookies and references alive, stale handles could not close their own contexts, and anonymous shared-browser disconnect listeners retained closed hosts. The implementation now has a background cleanup interval of at most 1 second, deletes expired/consumed approvals, closes contexts on handle expiry, lock/epoch change or credential record/status/policy invalidation, and removes closed tabs/sessions/associated approvals. Default caps are 8 open sessions (including pending openings) and 32 pending approvals, with hard configuration ceilings of 32/128. Failed context setup closes allocated contexts. Host close clears the timer, detaches its named browser listener, closes contexts and awaits cleanup. The private owner cleanup method accepts a stale owned handle without granting browser actions; unauthorized principals cannot close another live session. `control.prune()` lets the trusted owner await immediate cleanup when needed. Navigation invalidates approvals while the bounded host context remains available for the separately demonstrated post-login session lifecycle, until its handle TTL or explicit close.

Real regression tests wait for filled Chromium pages to close while idle after expiry, epoch, record, status or policy changes; test stale-owner cleanup and other-principal refusal; exercise session/approval caps and freed capacity; and compare actual shared-browser disconnected listener counts across repeated host creation/closure. Additional review fixes select the session's bound rule for same-origin framed submission instead of the first rule with that origin, and terminalize a failed journal dispatch transition as `failed_before_dispatch` without network. Tests cover successful submission using the second same-origin frame rule and replay of a denied dispatch without leaving `accepted` indefinitely. A final regression additionally makes the synthetic site commit login and issue its authenticated session cookie before returning HTTP 500. The browser returns `outcome_unknown`, the cookie really grants the synthetic account, replay across journal restart returns the stored result, and a new ticket cannot produce a second POST. Final build, standalone demo, and all 54 browser tests passed after these fixes, with fresh logs/results replacing earlier evidence.

## Remaining scope

The library + runnable synthetic demonstration is complete for this boundary. There is no claim of native browser integration for Muse/Grok/Dot/Hermes/DSH, production rule coverage, arbitrary website login, MFA/captcha automation, encrypted persistent browser profiles, or management approval UI/MCP wiring. A production integration must keep the approval surface private and retain core ticket, policy and journal semantics; it must not expose the trusted Page accessor or enable tracing/console forwarding/DOM secret read tools. Page content and fixed site rules are part of the trust boundary.
